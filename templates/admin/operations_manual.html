Use this guide for day-to-day administration of Cheradip. Each database tab shows its own tables. Your account permissions control which records and actions are available. Changes to customer balances, orders, and paid rights need a clear audit trail.

Accounts and permissions

Customers can be Students, Teachers, Job Seekers, or Others. Their website profile, Wallet, purchase history, and referral balance belong to the same customer account. Student and Teacher package families are separate purchases; any account type may use a purchased Teacher allowance. Exams are free to attend.

Open customers Staff permissions should be assigned by model and action. Staff status by itself does not grant marketplace write access; only a superuser or a staff account with the corresponding add, change, delete, or view permission may use an administration API. Grant the least access needed for the job.

Password recovery codes go only to an existing saved contact. Codes expire after ten minutes, are limited to five attempts, and are valid only for their stated purpose. A user can change a saved email after signing in and confirming the current password. Do not ask a customer to send a password or verification code to staff.

Packages, renewal, and badges

Student and Teacher plans have independent Academic, Admission, and Combined tracks. Combined covers both tracks in its own package family. Each customer receives the applicable introductory Free period once. Student Free lasts one month plus seven days of grace; Teacher Free lasts 36 months. A paid package replaces Free in that family.

Higher plans charge on activation. A lower plan may be selected without another charge while an allowance remains. When the Teacher question allowance is exhausted, another allowance needs a paid activation. Same-plan selection before expiry shows the existing renewal date. Automatic paid renewal checks the Wallet when due; insufficient funds start a seven-day grace period with limited warnings, then the package is cancelled.

Teacher question creation counts the stored question sets according to the package rules. Badge progress considers recent activity as well as lifetime totals; discounts apply to the next renewal and referral value uses the current eligible badge. Check the customer's package and progress records before correcting a reported allowance. Historical rows are kept for order tracking.

Wallet, recharge, referral, and withdrawals

100 Coins equal Tk 1. The main Wallet contains all spendable Coins. The reference balance is the still-withdrawable part earned through referrals. A purchase uses reference value first and reduces both that part and the main Wallet; the same value cannot also be withdrawn. Withdrawal requests reserve their amount immediately. Staff approve only after sending the payout manually and confirming the recipient and amount; rejection releases the reservation once.

Transaction ID intake requires the private TRX_INGEST_SECRET configured on the backend and sent by the trusted intake device in X-Cheradip-Ingest-Key. It accepts BDT and bounded positive amounts. Imported historical transaction rows start unverified and cannot credit a Wallet until staff check them. Inspect a receipt against the payment provider's official record, then mark the transaction verified. Duplicate transaction IDs can credit at most once. Never put the intake secret in browser code or a public manual.

Do not edit a customer's balance JSON, a ledger entry, or a paid order directly to fix a discrepancy. Check the transaction, order, reference balance, and ledger together. Use the supported payment/order actions or a reviewed reconciliation procedure.

Marketplace, products, books, and orders

Manage categories, products, variants, prices, stock, images, books, and book files in the eCommerce database tab. A product must be active, its variant active, and stock available at checkout. Cart contents are tied to the purchasing account once claimed. A completed checkout has one order ID. Product and book orders remain pending for staff fulfilment even if a Wallet payment has been received. Package orders are completed automatically after successful Wallet payment.

CSV import supports the downloadable sample from the marketplace administration API. Include Handle, Title, Product Category, SKU and Price headers. Every new SKU needs Price and Inventory Quantity. On an existing SKU, a blank Price or Quantity leaves the current value unchanged; negative or nonfinite prices are rejected. Review the import's row errors and created/updated counts before publishing products. The saved variant stock is authoritative after sales.

For a book, upload a cover and its public sample separately from the paid manuscript. eBook files are stored privately and become downloadable only for a completed, paid order containing the digital variant. A hard-copy purchase does not grant digital access. The customer sees orders under Purchase History and can track an order by its ID.

Confirm payments and change order status through the order/payment controls. Cancelling or refunding a Wallet order credits it once and restores eligible stock once. A refunded payment cannot subsequently complete the same order. If a settlement was interrupted, run the reconciliation report first; do not confirm by editing raw rows.

Questions, exams, exports, and AI tools

The education database tabs contain subjects and question tables. Question creation, explanation updates, exam generation, and review jobs are managed from each database's Settings page. The selected level, class, subject, chapter, and topic determine the scope. Review AI-generated content and its source question before approval. Published question lists do not send locked answers or explanations to visitors; the server provides the solution after a valid entitlement or Coin unlock.

MCQ exam grading uses the exact saved option text when an answer is ambiguous, especially for numeric choices, before interpreting a marker. Each new exam attempt freezes its question and answer snapshot. Availability dates are checked on the server. Exam attendance is free; reports and ranks use the saved result. Historical grading changes must be reviewed separately before changing old results or badge calculations.

PDF and Word exports preserve question formatting, images, and answer/explanation labels. The website Tutor can use curriculum context and configured AI providers; user-owned keys remain tied to that user. The AILT mobile service is a separate FastAPI application under /ailt/api/.

Institutes and EIIN details

The `/institutes/<EIIN-name>` detail page is public, including available Banbeis details and the imported EMIS staff roster. It does not require an account or deduct Coins. Vacancy and recommendation pages still use their separate EIIN unlock: an active paid package grants access without a debit, while a Coin purchase lasts two years. Those pages continue to mask protected Banbeis fields and staff contacts until their own entitlement is valid. Do not put individual EMIS staff contacts in institutional contact fields.

Older locally saved EIIN lists cannot prove a payment. If a customer reports a previous paid unlock, check their transaction and support record and restore only verified entitlements through the controlled administration process. Never copy a browser list directly into the server-owned entitlement field.

Question and institute scraping

Open scraping workspace The link is shown only to staff or administrators. The workspace has separate Questions and Institutes tabs. Its backend endpoints also check staff access; a normal customer cannot run an import by typing the URL.

On the Institutes tab, Update reads six-digit EIINs already in Cheradip's institute database in order and checks each one against Banbeis, with EMIS enrichment when available. Keep the page open while batches run; Stop pauses after the current batch, and Update resumes an unfinished run. The server stores one completed.txt and one failed.txt per run in the displayed private log directory. Completed includes unchanged institutes and EMIS-only warnings; a failed Banbeis fetch or save goes to the failure file with its reason. Update on Failed reads EIINs from that run's failure text file and retries them once per click. A successful retry moves the EIIN to completed and removes it from failed. Download either file from the staff workspace.

Public institute detail visits also request a background check when that EIIN was not checked successfully in the past 24 hours. Duplicate requests are combined, and the page shows saved data while waiting. The separate institute worker starts a full pass on the last day of each month (Bangladesh time), resumes after restarts, and retries each remaining failed EIIN up to three times after the pass. It keeps the current and previous two calendar months of completed success/failure logs and public-check events; older audit records are removed without deleting institute data. Local runserver starts this worker automatically. On production, enable the separate systemd worker described in deploy/INSTITUTE-MONTHLY-UPDATE.md; otherwise requests stay queued.

Advanced controls remain available for one EIIN or a Banbeis directory page. For page imports, choose a start page, 1–25 records per page, and 1–100 pages for a run. Only completed batch pages are saved as checkpoints; one-EIIN updates do not change the batch position. A failed page is not checkpointed: review the error and retry the same page. Existing EIINs are updated, not duplicated, and fields absent from a source response are preserved.

Banbeis supplies the public institute detail, institutional contacts, post office, ward, establishment, management, and location information. The full verified response is kept in a source snapshot. EMIS supplies a separate public staff roster, matched by EIIN and institute name; it includes support staff, designation, subject, available joining dates, PDS/index IDs, district, BCS batch, contact details, and safe photo URLs. Staff are ordered by designation and then oldest available joining date in one responsive grid; many EMIS rows currently have no joining date. EMIS names fill only an otherwise missing Banbeis name. Empty or mismatched rosters leave saved staff unchanged. If EMIS is unavailable, Banbeis updates continue and the run records a warning. The Banbeis annual-survey host currently fails HTTPS validation from this server; existing student statistics are preserved, not guessed or erased.

Database tabs, review markers, and notifications

Each database tab shows its own tables. Circled counts indicate observed changes or pending work. Visiting a table acknowledges ordinary change events for that staff user; pending orders, payments, withdrawals, and question reviews remain marked until resolved. The raw table editor checks both the owning database and model permissions; credential fields are masked.

Direct SQL, imports, and separate services do not emit Django model events. Run python manage.py scan_admin_table_changes during off-peak maintenance to compare table fingerprints. The first run establishes a baseline, and later runs report changed tables. External AILT and Agent tables are read-only here. A change marker indicates a detected difference, not an exact count of edited rows.

Deployment, sync, and troubleshooting

  1. Back up the primary, education, and eCommerce databases and media before release. Apply pending migrations to their owning database, then deploy matching backend and frontend versions.
  2. Check python manage.py check --deploy. Verify sign-in, public question lists, institute search, package access, checkout, order tracking, and the admin page using a test account.
  3. Use python manage.py protect_ebook_files to report old public files. Review the report before --apply. Keep the private eBook directory outside public media and back it up separately.
  4. Use python manage.py reconcile_commerce_wallets as a read-only report first. After reviewing committed ledger entries and affected orders, --apply only acknowledges already committed debit/refund operations.
  5. mysql_db_sync --l2r ensures only that project databases and tables exist remotely; it does not copy records or alter existing tables. --l2rd also inserts missing local records and updates matching remote records, while preserving remote-only rows. Review its dry-run output before using it against production. Apply migrations to add columns. A missing database is created when the remote account has permission; otherwise follow the command's instructions and grant access. The reverse --r2l snapshot copies remote tables and data to local and needs a separate backup and deliberate authorization.

When something appears wrong, note the page, customer/order/EIIN ID, time, expected result, and actual result. Check the relevant database tab, status history, and ledger before changing any record. Contact support or a superuser for permission or payout disputes.
