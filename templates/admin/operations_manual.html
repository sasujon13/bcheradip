Accounts and permissions

The Cheradip database lists Users & customers, User groups, and User permissions. Users & customers is the existing cheradip_customers table, including accounts created with createsuperuser; there is no second user table. Each customer row has a Permissions link, and the customer list/editor links directly to groups and permissions.

Create named permission groups (for example, Catalog Manager or Order Support), select the existing permissions needed by each role, then assign those groups to customer accounts. Individual permissions can be added or removed separately. Staff access enables administration login and the marketplace Manage menu; group/individual permissions determine available features. Administrator grants full access. Student/Teacher/Job Seeker/Others remain profile categories, not security roles.

Superusers can create, edit, and delete groups and permission definitions using their registered administration pages. Normally assign existing permissions instead of changing built-in permission names/codenames or deleting them: those definitions are referenced by application checks. A new custom permission does not create a new feature automatically. Use Add user for password-validated account creation; passwords are hashed, not stored as plain text. Administrator password resets invalidate existing website tokens.

To give an existing user administration access, sign in as an existing Administrator (superuser), open Customers & admin access, choose that account, and expand Administration & marketplace access. Select Staff access and the required Individual permissions or Permission groups. Administrator — full access grants all permissions, including permission to promote other users; reserve it for trusted site administrators. Save, then sign in to the website using that same account. No separate administrator account table is created. A Teacher or Student profile category alone does not grant staff access.

Customers can be Students, Teachers, Job Seekers, or Others. Their website profile, Wallet, purchase history, and referral balance belong to the same customer account. Student and Teacher package families are separate purchases; any account type may use a purchased Teacher allowance. Exams are free to attend.

Open customers Staff permissions should be assigned by model and action. Staff status by itself does not grant marketplace write access; only a superuser or a staff account with the corresponding add, change, delete, or view permission may use an administration API. Grant the least access needed for the job.

Password recovery codes go only to an existing saved contact. Codes expire after ten minutes, are limited to five attempts, and are valid only for their stated purpose. A user can change a saved email after signing in and confirming the current password. Do not ask a customer to send a password or verification code to staff.

Packages, renewal, and badges

Student and Teacher plans have independent Academic, Admission, and Combined tracks. Combined covers both tracks in its own package family. Each customer receives the applicable introductory Free period once. Student Free lasts one month plus seven days of grace; Teacher Free lasts 36 months. A paid package replaces Free in that family.

Higher plans charge on activation. A lower plan may be selected without another charge while an allowance remains. When the Teacher question allowance is exhausted, another allowance needs a paid activation. Same-plan selection before expiry shows the existing renewal date. Automatic paid renewal checks the Wallet when due; insufficient funds start a seven-day grace period with limited warnings, then the package is cancelled.

Teacher question creation counts the stored question sets according to the package rules. Badge progress considers recent activity as well as lifetime totals; discounts apply to the next renewal and referral value uses the current eligible badge. Check the customer's package and progress records before correcting a reported allowance. Historical rows are kept for order tracking.

Wallet, recharge, referral, and withdrawals

100 Coins equal Tk 1. The main Wallet contains all spendable Coins, including the Tk 50 (5000 coin) signup bonus. Those coins can pay for shop products, packages, and other Cheradip services, but they are not withdrawable. The reference balance is the still-withdrawable part earned through referrals. A purchase uses reference value first and reduces both that part and the main Wallet; the same value cannot also be withdrawn. Withdrawal requests reserve their amount immediately. Staff approve only after sending the payout manually and confirming the recipient and amount; rejection releases the reservation once.

Transaction ID intake requires the private TRX_INGEST_SECRET configured on the backend and sent by the trusted intake device in X-Cheradip-Ingest-Key. It accepts BDT and bounded positive amounts. Imported historical transaction rows start unverified and cannot credit a Wallet until staff check them. Inspect a receipt against the payment provider's official record, then mark the transaction verified. Duplicate transaction IDs can credit at most once. Never put the intake secret in browser code or a public manual.

Marketplace, products, books, and orders

Website Business Manager

Open Business Manager The marketplace menu shows Manage immediately after Cart for signed-in admin/staff accounts only. Ordinary customers cannot open its private records or use its management APIs. Sign in to the website with your staff account; a separate Django session is also supported with its normal CSRF protection. A website login does not gain permissions from another account's Django session.

Staff status alone is not enough to edit records. Assign the appropriate eCommerce view/add/change permissions for products, variants, images, orders, payments, and other required models. Stock adjustments require both add inventory movement and change product variant. Product photo removal additionally requires delete product image. A superuser has all these capabilities. Do not give superuser access merely to let someone upload products.

  1. Create or choose a category and optional brand.
  2. Open Products → Add product. Enter the name, unique URL name, description, specifications, and at least one variant with a unique SKU, price, and stock.
  3. Upload JPG, PNG, or WebP photos (up to 5 MB each). Photos are validated, resized, and stored as WebP. Choose Active only when the product is ready to sell.
  4. For many products, download the sample CSV from CSV imports, fill its columns, then import and review the saved row-by-row report.
  5. Use Orders and Payments to review purchases and confirm changes explicitly. Shipping stores delivery tracking details; update the order's status separately. Inventory adjustments retain a stock audit trail.

The manager also provides categories, brands, discounts, review moderation, business notifications, and links to book/ebook publishing, customer administration, stock history, and this manual. Books and advanced settings continue to use their existing Django editors. Nothing is approved, charged, or refunded just by opening a page.

Manage categories, products, variants, prices, stock, images, books, and book files in the eCommerce database tab. A product must be active, its variant active, and stock available at checkout. Cart contents are tied to the purchasing account once claimed. A completed checkout has one order ID. Product and book orders remain pending for staff fulfilment even if a Wallet payment has been received. Package orders are completed automatically after successful Wallet payment.

CSV import supports a rollback-only preview before confirmation. Include Handle, Title, Product Category, SKU and Price headers. Every new SKU needs Price and Inventory Quantity. An existing SKU cannot move to another product. Blank Price or Quantity preserves the current value. For stock changes, Expected Inventory Quantity must match current stock, so concurrent sales are not overwritten. Upload at most 10 MB per batch and review row errors before confirming.

Courier and COD charges: Normal delivery uses stored weight × quantity and the midpoint of eligible minimum/maximum courier base fares. The reviewed profiles assume Dhaka metro pickup; confirm exact coverage, bulky/fragile handling and carrier tax/COD before dispatch. Missing weights explicitly use fallback Tk80 for Dhaka district or Tk120 outside; known unsupported weights require a manual quote. Change profiles and fallback fees in Delivery & store settings or Marketplace → Manage → Delivery & policy. Product fixed-fee overrides contribute once per distinct product; zero is included in the midpoint. COD remains 1% by default, on discounted goods only, never delivery; wallet/prepaid have no COD surcharge. Digital-only orders have no courier fee. Existing orders retain accepted charges and rate snapshots. Checkout prefills editable contact/address fields; changed totals need review. CSV charge cells accept DEFAULT to restore inheritance; blank preserves overrides.

Listing price calculator: Marketplace → Manage → Products → Add/Edit → variant. Source cost stays product-specific. Central planning defaults are ads Tk20, packaging Tk11, return reserve Tk48.75 and other costs Tk0; these are estimates, not audited national averages. Use an actual supplier packaging quote instead of the packaging estimate when verified, never both. Research links and editable courier bands are in Delivery & policy. Delivery subsidy is OFF unless explicitly enabled by the owner; supplier delivery is separate from the product-only market benchmark. Uncheck central defaults for manual variant costs. Markup on all costs is 20% through Tk100 inclusive, 19% through Tk200, decreasing one point per Tk100 to 10% above Tk1000. Band-boundary price drops are possible. Calculate is read-only; Apply changes the draft; Save respects activation and supplier-publication safeguards. Costs stay private; edits never silently reprice products. Native Django variants have the same opt-in calculator. CSV Use Default Costs=TRUE selects inheritance; only Apply Calculated Price=TRUE changes price. Existing orders never reprice; estimates, taxes, multiple parcels and discounts can reduce actual profit.

The normal deployment enables cheradip-commerce-maintenance.timer to run about every five minutes. Pending unpaid reservations expire after the configured duration (default 24 hours), returning stock once; submitted payment evidence is left for staff review. The worker reconciles already committed wallet entries without charging again and sends receipts only for new orders. After five failed email attempts it creates a staff notification. Inspect journalctl -u cheradip-commerce-maintenance.service for failures. Staff need explicit ecommerce permissions; staff status alone does not grant access to other customers' orders.

For a book, upload a cover and its public sample separately from the paid manuscript. eBook files are stored privately and become downloadable only for a completed, paid order containing the digital variant. A hard-copy purchase does not grant digital access. The customer sees orders under Purchase History and can track an order by its ID.

Confirm payments and change order status through the order/payment controls. Cancelling or refunding a Wallet order credits it once and restores eligible stock once. A refunded payment cannot subsequently complete the same order. If a settlement was interrupted, run the reconciliation report first; do not confirm by editing raw rows.

These charges take priority and are used directly, never averaged with other courier quotes. Weight times quantity determines the band. Different products remain separate shipments unless a supplier-confirmed shipment group and matching tariffs permit consolidation. Missing weights, missing area coverage or excessive weight require manual review. Ordinary products without supplier tariffs keep their existing area/weight calculation.

Delete removes a product and its variants/photos permanently. Products with order history remain protected in the API and Django. Separately verified disposable samples can be purged only with the narrow remove_test_commerce command; it refuses payment, wallet, supplier, shipment and financial links and creates a private recovery backup. Never use it for real customer orders.

Deployment, sync, and troubleshooting

Automatic catalog sync: the Windows task Cheradip Catalog Two Way Sync checks every two minutes while the configured Windows user is signed in and connected. Django admin and Manage catalog edits synchronize through the existing trusted SSH connection. Run bcheradip\venv\Scripts\python.exe deploy\sync-catalog.py from the project directory for a manual cycle. Product/source IDs are mapped with stable identities instead of assuming equal row numbers. Independent fields merge; conflicting edits use the later timestamp and a deterministic tie-break. Actual supplier observation times protect newer price/stock facts. Original cached product photos transfer before new listings activate. Individual collection outcomes, failure reasons and retry checkpoints also synchronize, including a one-time backfill of older outcome records. The initial full reconciliation can take considerably longer than incremental checks. Offline changes wait for reconnection. The Suppliers page shows the last sync activity; private reports and the durable checkpoint are in bcheradip/private_suppliers/catalog_sync/.

Catalog sync excludes customers, orders, wallets, payments, supplier credentials and financial ledgers. It propagates archives and catalog settings, but does not propagate physical deletion as an automatic destructive operation; archive listings to remove them from both shops. Preserve the first private full-sync snapshot and ordinary database/media backups. Do not use a broad database restore to repair a catalog mismatch. Review the conflict report before resolving competing staff edits. See deploy/CATALOG-AUTO-SYNC.md for verification, recovery and limitations.

  1. Back up the primary, education, and eCommerce databases and media before release. Apply pending migrations to their owning database, then deploy matching backend and frontend versions.
  2. Check python manage.py check --deploy. Verify sign-in, public question lists, institute search, package access, checkout, order tracking, and the admin page using a test account.
  3. Use python manage.py protect_ebook_files to report old public files. Review the report before --apply. Keep the private eBook directory outside public media and back it up separately.
  4. Use python manage.py reconcile_commerce_wallets as a read-only report first. After reviewing committed ledger entries and affected orders, --apply only acknowledges already committed debit/refund operations.
  5. mysql_db_sync --l2r ensures only that project databases and tables exist remotely; it does not copy records or alter existing tables. --l2rd also inserts missing local records and updates matching remote records, while preserving remote-only rows. Review its dry-run output before using it against production. Apply migrations to add columns. A missing database is created when the remote account has permission; otherwise follow the command's instructions and grant access. The reverse --r2l snapshot copies remote tables and data to local and needs a separate backup and deliberate authorization.

When something appears wrong, note the page, customer/order/EIIN ID, time, expected result, and actual result. Check the relevant database tab, status history, and ledger before changing any record. Contact support or a superuser for permission or payout disputes.
